# writeGameState: 12.7x, and the ISA the training module actually uses

*2026-09-21 — branch `perf/engine-optimizations`, commit `dce5f4b`*

## The target

`Game::writeGameState` builds the neural network's input vector. It ran once per
node that requests an evaluation, which is most nodes, and it looked like this:

```cpp
for (int32_t i = 0; i < 4 * kBoardSize; ++i) {
  if (board_[i]) {
    game_state[i] = 1.0;
  } else {
    game_state[i] = 0.0;
  }
}
```

Sixty-four iterations, each testing one bit and storing one float. The branch is
on board contents, so it mispredicts constantly — this was the largest single
source of branch mispredicts left in the engine.

It was measured at **88.6 ns** against `getLegalMoves` at 137.9 ns, and roughly
4.4% of program instructions — about 19x `Game::doMove`, which is why entry 07
ended by pointing here.

## The finding that shaped the fix

**`setup.py` passes no `-march`.** The training module is therefore compiled for
baseline x86-64 — SSE2, no AVX2 — while `bench/Makefile` uses `-march=native`.

Anything tuned under `-march=native` is not necessarily what training runs. This
is worth remembering for every future optimization on this branch, not just this
one.

So all candidates were measured under both. `data/writegamestate/variants.cpp`,
ns per call for expanding 64 bits into 64 floats, verified against the current
implementation for correctness first:

| variant | baseline x86-64 | `-march=native` |
|---|---|---|
| A current (`bitset[]`) | 204.38 | 199.32 |
| B branchless scalar | 31.97 | 33.64 |
| **C nibble table, 256 B** | **3.56** | **3.47** |
| D byte table, 8 KB | 5.87 | 2.18 |
| E SSE2 intrinsics | 7.19 | 7.22 |
| F AVX2 intrinsics | n/a | 5.14 |

Read that table carefully, because it inverts:

- **The 8 KB byte table is the fastest under `-march=native` and among the
  slowest without it.** With AVX2 the 32-byte row is one `vmovups`; without it,
  two 16-byte moves plus worse code around them. Picking D on the strength of a
  `-march=native` benchmark would have shipped the second-slowest table variant.
- **Hand-written AVX2 (F) loses to a plain table (D) on the same ISA.** The
  compiler generates better code for `memcpy` of a table row than the obvious
  broadcast/and/cmpeq sequence.
- Simply making the scalar loop branchless (B) is a 6x win on its own and needs
  no table at all. Most of A's cost was the mispredicting branch, not the work.

### Why C

The nibble table is fastest on the ISA that actually ships, within 60% of the
best native figure, needs no intrinsics or runtime dispatch, and keeps the L1
footprint at **256 bytes rather than 8 KB**.

That last point is not incidental. Entry 07 established that this engine is fast
because its working set stays in L1 — a `Game` is 16 bytes, a `Node` is 64, and
the DRAM miss rate is 0.029%. Spending a quarter of a 32 KB L1 on a lookup table
to win 1.3 ns per call would be trading the property the whole engine depends on
for a local optimum.

It also happens to fit the data exactly: the board stores four bits per space —
base, column, capital, frozen — so **one space's nibble is precisely one group of
four network inputs.** The table is "what one space expands to", all sixteen
possibilities.

```cpp
const uint64_t board = board_.to_ullong();
for (int32_t space = 0; space < kBoardSize; ++space) {
  std::memcpy(game_state + space * 4,
              kNibbleFloats.value[(board >> (space * 4)) & 0xF],
              4 * sizeof(float));
}
```

Generated by `constexpr`, not transcribed.

## Results

Micro, interleaved and pinned to a P-core, 7 reps per arm:

```
Game::writeGameState   90.0 ns -> 7.1 ns     12.7x
```

(7.1 ns includes the six piece counts, which this change does not touch; the
64-bit expansion alone is the 3.5 ns from the table above.)

End to end, exact counters, fixed 3-game run:

| counter | old | new | delta |
|---|---|---|---|
| instructions | 1,024,579,778 | 989,516,124 | **-3.42%** |
| data writes | 51,285,515 | 46,899,324 | -8.55% |
| branches | 111,762,864 | 100,066,367 | -10.47% |
| **branch mispredicts** | 7,336,950 | 5,832,167 | **-20.51%** |

Data writes fall because sixty-four 4-byte stores become sixteen 16-byte copies.

Wall clock, 120 games single-threaded and pinned, 9 interleaved reps
(`data/writegamestate/wall-120games-st.txt`):

```
old  min 3.404  median 3.475
new  min 3.217  median 3.253
     -5.48% on min-to-min, -6.37% on medians
```

### The wall figure exceeds the instruction figure, and that is correct

-6.4% wall against -3.42% instructions is not a contradiction and not noise. It
is entry 07's cost model producing a prediction that then held:

```
1,504,783 fewer mispredicts  x ~17 cycles  ~= 25.6M cycles
   35.1M fewer instructions  / 6 wide      ~=  5.8M cycles
                                              -------------
                                              ~31M of ~387M  ~= 8% ceiling
```

Observed 5.5-6.4%, under the ceiling because the terms overlap on an
out-of-order core. A mispredict costs ~17 fully exposed cycles but retires as
one instruction, so instruction count systematically undercounts the value of
deleting an unpredictable branch.

This is the clearest case on the branch of why Ir and Bcm have to be read
together.

## Follow-ups this raised

- **`setup.py` has no `-march`.** Worth deciding deliberately rather than by
  omission. `scripts/bash/build.sh` compiles on the target machine, so
  `-march=native` would be safe there and is not safe if a built module is ever
  copied between machines. Note that entry 03 measured `-march=native` as noise
  for the *then-current* code; that was before any of the bitboard work, so it
  is worth re-measuring rather than assuming it still holds.
- The six piece counts at the end of `writeGameState` are untouched. The
  `(to_play_ * 3 + i) % 6` indexing is a rotation by three and could be two
  copies, but it is six elements and was not measured as significant.
