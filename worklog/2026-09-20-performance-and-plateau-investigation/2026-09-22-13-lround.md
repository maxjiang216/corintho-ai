# 13 — `lround` in `setProbs`: −6.9% instructions, −3.8% engine time

Commit: see `git log -- corintho_ai/cpp/src/trainmc.cpp` (the one after 10d1e7d).

## How it was found

Max asked to work on node selection (`TrainMC::chooseNext`). Profiling HEAD for
that (`bench/profile.sh select-baseline deep` and `lines`) turned up two
non-selection costs that were larger than expected and much cheaper to fix:

| function | share of Ir (3 games × 1600 searches) |
|---|---|
| `lround` (libm) | 6.26% |
| `std::mt19937::operator()` (Dirichlet noise) | 5.89% |

This entry does the first. `mt19937` and selection are still open.

## The line

`TrainMC::setProbs` scales each move's prior-plus-noise so the largest becomes
511 (`Node::kMaxProbability`) and rounds it into the 9-bit `Edge::probability`:

```cpp
int32_t prob = std::max(
    1, gsl::narrow_cast<int32_t>(lround(weighted_probs[j] * denom)));
```

It runs once per legal move per received evaluation: 2,177,611 calls in the
profiled run.

## Why `lround` is expensive

`lround` rounds half away from zero and returns `long`. The standard also makes
it responsible for NaN, infinity and out-of-range results (`FE_INVALID`,
possibly `errno`), so GCC does not inline it without `-ffast-math`-style flags.
It is a PLT call into libm, ~30 instructions per call (65.3M / 2.18M in the
no-LTO line profile). Here the `float` argument was also widened to `double`.

`static_cast<int32_t>(x + 0.5f)` compiles to `addss` + `cvttss2si`: two inline
instructions, no branches, no call. Truncation after adding 0.5 is
round-half-up, which equals half-away-from-zero for positive values.

## Equivalence: checked exhaustively, not argued

The input is always in (0, 511], so NaN, overflow and negative values cannot
occur. `data/lround/exhaustive_check.cpp` compares the two over **every float in
(0, 511.5]** (1,140,834,304 values):

```
floats checked 1140834304, raw diffs 1 (first 0.49999997), diffs after clamp 0
```

The one disagreement is `0.49999997f`, where `x + 0.5f` rounds up to exactly
`1.0f` in float arithmetic. The existing `std::max(1, …)` maps both answers to
1. For x ≥ 0.5 the addition is exact in this range, so nothing else can differ.

**Correction to what I told Max beforehand:** I gave `2.4999998f` as an example
of a value that would round differently. It does not; that addition is exact.
Only values below 0.5 can lose bits, and the clamp covers them.

Golden digests are unchanged (game `d8f9bd2d22ee9731`, engine
`ad85cefa8bf9abf5`), as the exhaustive check predicts.

Wall clock: `selfplay_bench 50 1600 16 1 12345`, pinned with `taskset -c 0`,
11 reps, arms interleaved before/after, `engine_seconds`:

| | before | after | change |
|---|---|---|---|
| min | 1.2482 | 1.2067 | −3.32% |
| median | 1.2628 | 1.2161 | −3.70% |
| paired median | | | **−3.81%** |

Both arms did identical work in every run (1008 turns, 1,264,308 requests).
Spread within each arm was ~7%, but the paired, min and median views agree.
Raw runs are in `data/lround/ab-engine-seconds.txt`.

**Why time falls about half as much as instructions:** the removed instructions
were cheap ones — straight-line, perfectly predicted libm code running at high
IPC. Removing them saves fewer cycles per instruction than the program average.
This matches the cost model in entry 07: instruction count alone overstates the
gain when the removed code has no mispredicts or misses.

The bench stub's own work (`bench_util.h:main`, ~28% of Ir) is also in the
denominator, so the engine-only share is larger than −6.9%. In production the
network dominates wall time, so the end-to-end training gain is smaller still.

## Still open from this profile

- `mt19937` in `generateDirichlet`: 5.9% of Ir, one 32-bit draw per edge per
  evaluation, used only for `% kNumGammaBuckets`.
- `chooseNext`: ~43% of Ir (no-LTO) and ~3.0M of 5.85M mispredicts. It scores
  every legal move each call (25.8 on average), 39% of them unvisited, and only
  the highest-prior unvisited one can ever win. Sorting edges by prior would let
  the loop stop early. That is not bit-identical: tie-breaking order changes.
