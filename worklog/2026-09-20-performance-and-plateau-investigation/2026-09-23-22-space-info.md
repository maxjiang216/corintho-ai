# 22 — computeSpaceInfo without the per-space loop: −12% on the stub, −2.4% in production, and why the gap is the finding

The first engine change after entries 18–21 showed the engine is the bottleneck
again. The developer asked to look at `initializeEdges` (~15% of instructions
on the stub), and to do the legible changes before PGO and other compiler
work. Raw outputs are in `data/space-info/runs.txt`.

## What `initializeEdges` is

`initializeEdges` calls `game_.getLegalMoves()`, allocates an `EdgeBlock` from
the arena, and writes one `Edge` per legal move. Almost all of its cost is
`getLegalMoves`. The line-level stub profile from entry 16
(`bench/results/profiles/mirror-lines-ir.txt`) splits that:

| part | share of all instructions |
|---|---|
| `getLegalMoves`, inclusive | 10.65% |
| `computeSpaceInfo` | **6.06%** (~680 instructions per call) |
| `findLines` | 3.07% |
| `basicLegalMoves` | 1.07% |
| `lineBreakers` | 0.09% |

## Why this was left over

Entries 02–05 rebuilt `getLegalMoves` in stages:

1. Stage 1: compute per-space state once. This added `computeSpaceInfo`, which
   replaced ~150 recomputations per call.
2. Stage 2: emit legal moves from whole-board masks.
3. Line detection with shifted masks.
4. The 4-bits-per-space board word (entry 07).

Stage 1's single pass stayed a loop over 16 spaces with branches. It was a
large win at the time, so nobody revisited it. After the other stages made
everything around it nearly free, it was 57% of what remained.

Entry 02 had planned a "Stage 3: bit-plane board", four separate 16-bit planes,
which would have made this natural. Entry 05 marked that stage done through
the nibble layout, but `computeSpaceInfo` never stopped going space by space.
This change completes it without changing the board layout.

## The change

The board is one 64-bit word, 4 bits per space: base, column, capital, frozen.
Piece type *t* for all 16 spaces is bit *t* of every nibble.
`gatherNibbleBits(x)` collects bit 0 of each nibble into a 16-bit mask. It
uses five shift/OR/mask steps, doubling the group width each time
(1 → 2 → 4 → 8 → 16). So:

```cpp
base    = gatherNibbleBits(b >> kBase);
column  = gatherNibbleBits(b >> kColumn);
capital = gatherNibbleBits(b >> kCapital);
frozen  = gatherNibbleBits(b >> kFrozen);
empty   = ~(base | column | capital);
top_plane[kCapital] = capital;
top_plane[kColumn]  = column & ~capital;
top_plane[kBase]    = base & ~column & ~capital;
```

This is SWAR ("SIMD within a register"): ordinary integer shifts and masks
acting on 16 spaces packed into one word. It uses no vector ISA. BMI2 `pext`
would do each gather in one instruction, but it would need BMI2 compiled in,
for a saving of a few instructions. Not taken.

The per-space `top[16]` and `bottom[16]` arrays are gone. Only two rare paths
read them:

- `lineBreakers`, which runs only when lines exist, ~15% of positions;
- `canMove`, behind `isLegalMove`, which move generation does not use.

They are now `SpaceInfo::top(space)` and `bottom(space)`, derived from the
planes on demand. `static_assert`s check `gatherNibbleBits` at compile time.

## Measurements

| workload | engine time | 95% CI |
|---|---|---|
| stub, 1 thread pinned to a P-core, 20 seeds × 40 games | **−12.0%** | −12.6 to −11.5 |
| real network, 1 thread pinned, 12 seeds × 120 games | **−4.9%** | −6.0 to −3.9 |
| real network, 20 threads, 6 seeds × 1,000 games | **−2.4%** | −3.4 to −1.4 |

Callgrind on the stub, 3 games: 617.9M → 586.1M instructions (−5.1% of the
program, ~−8% of the engine's share).

A single-threaded callgrind job was running on one core during these runs.
Interleaving puts its effect on both arms equally.

## The finding: the gain halves at each step toward production

- **Stub → real network, 1 thread: −12% → −4.9%.** The real network's trees
  are larger, so more time goes to walking them (selection, backup), which
  means pointer chasing over more memory. Node creation, where this change
  lives, is a smaller share.
- **1 thread → 20 threads: −4.9% → −2.4%.** With 20 threads the engine
  appears memory-bound: threads wait on cache misses, and removing
  instructions matters less.

The consequence for choosing targets: **stub instruction counts overstate
production gains, possibly several times over.** Two things follow:

- Rank candidates on real-network multithreaded time, not stub callgrind.
- Changes that reduce memory traffic in the tree may be worth more in
  production than instruction cuts: smaller or more local nodes, and fewer
  pointer hops in selection.

Not yet verified: that the 20-thread engine is memory-bound. The direct test
is 1-thread vs 20-thread scaling on identical games, with the real network.
It is next.

## Addendum: the real-network profile (before this change)

A callgrind run of the engine alone with the real network finished partially.
It used `--toggle-collect='Trainer::doIteration*'`, which leaves `Mlp` out,
and ran on the pre-change binary (`data/space-info/real-network-profile-before.txt`).
10 games, 1 thread, 1.7B engine instructions:

| part (LTO inlines most of it into `TrainMC::doIteration`) | Ir | L1 data misses |
|---|---|---|
| `trainmc.cpp` (search, selection, backup) | 46.3% | 47.8% |
| `node.cpp` inlined into it (accessors, `chooseNext`) | 21.6% | 19.6% |
| `initializeEdges`, all parts (`game.cpp` move generation 8.9%) | ~19% | ~2% |
| `syncStats` | 6.2% | **15.3%** |

- Move generation is ~9% of engine instructions with real trees. That is in
  line with the −4.9% single-thread gain above.
- `syncStats` (entry 16's mirrored child statistics) costs few instructions
  but a disproportionate share of L1 misses. It writes into the parent's stats
  block, so it is a memory-traffic candidate.
- At 10 games the working set fits in the 24 MB last-level cache: 116
  last-level misses in total. **This profile cannot show the memory pressure
  of 1,000+ games.** That needs the scaling test, or cachegrind at scale.
- Cost: callgrind still simulates `Mlp`'s arithmetic while collection is off,
  so this took over an hour. Next time run without `--cache-sim` and
  `--branch-sim` for instruction counts, or feed a cheap evaluator that
  replays recorded network outputs.
