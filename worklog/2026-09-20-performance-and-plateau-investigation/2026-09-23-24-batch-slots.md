# 24 — Fixed batch slots: the serial gather is gone, −16% engine+gather at 20 threads

This implements target 1 from entry 23. Commits: `5db3169` (the change) and
`7f05b8a` (Makefile header dependencies, found on the way). Raw outputs are in
`data/batch-slots/runs.txt`.

## The problem

Every iteration, `Trainer` counted every game's requests (`num_requests`) and
then copied all their rows, on one thread, from each game's private
`to_eval_` buffer into a packed batch (`writeRequests`). At the top of
`doIteration`, another serial walk turned the counts into offsets for reading
the results back. The copy is ~5–9 MB per iteration, bound by one core's
memory bandwidth. It cost ~1.2–1.5 s per 1,000 games at any thread count:
16% of engine time at 20 threads (entry 23).

## Two designs considered, and the measurement that chose between them

1. **Count, prefix sum, write in place.** Search, then a serial prefix sum
   over the counts (microseconds), then each game writes its rows at its
   offset in parallel. The batch stays packed.
2. **Fixed slots.** Each game owns `searches_per_eval` rows and writes them
   during search, the way it wrote into `to_eval_` before. There is no count,
   offset or copy, but slots a game does not fill are holes that still get
   evaluated.

The developer expected few games to produce fewer than 16 rows. Measured
(entry 23 addendum): **98.9% of active game-iterations fill all 16 rows, and
15.91 rows on average (99.4%)**. That measurement also corrected an error of
mine: I had been quoting ~12.5 rows per game, from 1,255 requests per 1,600
searches. But a descent ending on a terminal position does not end the batch;
`TrainMC` keeps searching until it has 16 rows. So fixed slots were chosen for
training.

## The first version was a net loss: finished games

The first implementation gave game *i* slot *i* and sent the prefix of
started slots. Three A/B pairs at 1,000 games:

| | packed | fixed slots, no compaction |
|---|---|---|
| gather | 1.46 s | 0.0007 s |
| rows evaluated | 35.7M | **52.8M (+48%)** |
| wall | 31.2 s | 41.1 s (+32%) |

In this harness every game runs in one batch and nothing replaces a finished
game. A finished game's slot stayed in the batch, empty, until the last game
ended. My slot-fill histogram had counted only active games, so it missed
this. I had also called the end-of-run tail "a few percent" without checking.
It is the largest effect.

## The fix: keep active slots a dense prefix

- A game takes the next free slot when it starts. The staggered start is
  unchanged: games start in index order.
- When a game finishes, the game in the **last** active slot moves into its
  place. That is one copy of the moved game's pending rows (≤16 rows, 4.5 KB),
  plus repointing its buffer (`SelfPlayer::set_to_eval` → both `TrainMC`s).
  So there is one small copy per finished game, not one full copy per
  iteration.
- `num_requests(-1)` = `searches_per_eval × active slots`. `Trainer::requests()`
  returns the batch for in-place evaluation.
- `writeRequests(-1)` still works for the other callers (golden,
  selfplay_bench, `main.pyx`). It is now one contiguous copy.
- Results come back in slot layout: game *g* reads `eval + slot_of_[g] × 16`.
- **Testing mode keeps packing.** Each call there serves only the games whose
  current player uses one model, and that set flips every move, so fixed
  slots would be ~50% empty.

In the future self-play driver, rolling starts do the same job naturally: a
new game takes the freed slot.

## Measurements (real network, 20 threads, interleaved)

| | 1,000 games, 4 seeds | 2,000 games, 2 seeds |
|---|---|---|
| **engine + gather** | **−16.3%** (95% CI −17.1 to −15.5) | **−16.6%** |
| gather | 1.40 s → 0.0002 s | 2.99 s → 0.0002 s |
| engine alone | −1.7% (CI −2.6 to −0.8): offsets loop removed | −1.1% |
| rows evaluated | +0.56% | +0.56% |
| CPU network (`Mlp`) | +3.3% (CI +1.2 to +5.3) | +4.2% |
| wall | −2.6% (CI −4.2 to −0.9) | −2.1% |

- **Engine + gather is the production number.** Wall time here is dominated by
  the CPU stand-in network, which the GPU replaces.
- The CPU network got ~3–4% slower, more than the 0.56% extra rows explain. A
  likely cause, not verified: the old serial copy left the batch warm in one
  core's cache just before the network read it, whereas now 20 threads write
  it during search. That is specific to the CPU backend; the GPU path reads the
  batch once for the transfer either way.

## Found on the way: stale objects in the bench build

`bench/Makefile` had no header dependencies, so changing `trainer.h` left
objects compiled against the old class layout. LTO reported them as One
Definition Rule violations, and `golden` printed nothing. Fixed with
`-MMD -MP` and `-include` of the `.d` files (`7f05b8a`).

Earlier header changes may have been built the same way:

- entry 22's `game.h` change only touched a private nested struct used in
  `game.cpp`, so no other object depended on it;
- every A/B in entries 18–23 used freshly created build directories.

So no earlier result is affected.
