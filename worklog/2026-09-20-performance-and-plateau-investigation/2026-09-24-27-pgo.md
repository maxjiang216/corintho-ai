# 27 — PGO: bit-identical, but no gain; the network's profile made it 3% slower

Profile-guided optimization (GCC 13.3) on the engine, in two unattended runs.
No engine code changed. Commits:

- `6d4a2c3`, `25f8002`: `bench/pgo_experiment.sh` and `bench/pgo_analyze.py`;
- `28f85e1`: run 1 results, `bench/results/pgo-2026-09-23/`;
- `b04667a`: run 2 results, `bench/results/pgo-2026-09-24/`.

Each results directory has `summary.txt` (everything below), `timing.tsv`,
`gates.txt` and `provenance.txt`. Run 2 also has `inspect.txt`.

## What PGO is (the developer asked)

Compile twice with a measured run in between:

1. build with `-fprofile-generate`;
2. run a representative workload, which writes branch and call counts to
   `.gcda` files;
3. rebuild with `-fprofile-use`.

GCC then lays out code, inlines and splits hot from cold using real counts
instead of guesses. It changes arrangement, not arithmetic, so it must be
bit-identical, and it was.

## The harness

`pgo_experiment.sh <model.mlp> [out]` is resumable like `long_profile.sh`,
with the same temperature logging and cooldown. It runs these steps:

1. **Build** `base` and an instrumented build.
2. **Train** the instrumented `selfplay_nn`: 300 real-network games, seed 777.
3. **Rebuild** each PGO arm from the profile.
4. **Gates:**
   - golden and verify for every arm;
   - `SAMPLE_DIGEST=1` on seeds 1–4 (300 games, 1600 searches, 20 threads),
     compared with the recorded baselines.
5. **Timing:** all arms back to back per seed, in rotated order:
   - `mt`: real network, 20 threads, 1,000 games;
   - `st`: stub, 1 thread pinned to CPU 0, 200 games.

`ARMS` selects the arms.

**Training is single-threaded.** Multi-threaded training needs atomic counters
(`-fprofile-update=prefer-atomic`). With 20 threads contending for the same
counters, 40 games took over 10 minutes instead of ~2 s, so that was dropped.
One thread takes the same branches in the same proportions.

**All object files share one directory.** GCC names each `.gcda` after the
object's full path, so the `-fprofile-use` build must write its objects where
the instrumented build did.

## Run 1 (overnight): PGO is slower

Arms:

- `pgo`: `-fprofile-use`;
- `partial`: `-fprofile-use -fprofile-partial-training`.

All gates passed, and turns were identical on every seed. Timing:

| | pgo | partial |
|---|---|---|
| mt, 40 seeds, engine | **+3.2%** (95% CI +3.0 to +3.4) | +3.5% (+3.3 to +3.7) |
| st, 40 seeds, engine | **+14.4%** (+13.9 to +15.0) | +15.2% (+14.5 to +15.9) |

The package averaged 91 °C. Every seed runs all arms back to back, so heat
does not favour one arm.

## Why: the network's counts set the bar for "hot"

**The binaries.** `objdump` of `TrainMC::doIteration`, which LTO inlines
almost the whole search into:

| arm | instructions | call sites | calls out of line on the search path |
|---|---|---|---|
| base | 2,547 | 23 | almost none (allocation, `Node::Node`, `initializeEdges`) |
| pgo | 1,591 | 34 | `syncFlags` ×6, `increase_evaluation` ×3, `Arena::get`/`allocate` ×3, `writeGameState` ×3, `set_evaluation`, `decrement_visits`, `promoteBestEdge`, … |

The vectorized selection survived: 32 packed divides in both.

**The profile.** Branch-counter totals per object (`gcov-dump -l`, arc
counters only; the value-profile counters hold raw values such as addresses
and must be excluded):

| object | total | largest single count |
|---|---|---|
| mlp | 3.8e11 | 1.6e11 |
| trainmc | 5.6e9 | 1.0e9 |
| node | 2.7e9 | 3.2e8 |
| game | 5.7e8 | 1.7e8 |

The CPU network is ~97% of all counts. GCC's cutoff for "hot" code is
relative to the program's largest count; the default is
`hot-bb-count-fraction=10000`, i.e. 1/10,000 of it, or ~1.6e7 here. The
training made ~1.3e7 searches (300 games × ~28 turns × 1,600), so
once-per-search code sat just below the bar.

**GCC's own report confirms it.** `-fopt-info-inline-missed` at the LTO link
says, for the pgo arm: `receiveEval -> increase_evaluation, call is unlikely
and code size would grow`. That call runs on every search.

## Run 2 (2026-09-24): removing the network's profile only restores neutral

Two new arms:

- `engine`: the same profile with `mlp.gcda` deleted;
- `frac`: the full profile with `--param=hot-bb-count-fraction=1000000
  --param=hot-bb-count-ws-permille=999`.

Each has its own fresh profile. All gates passed; turns were identical on 16
of 16 seeds.

| arm | doIteration instructions / calls | mt engine (16 seeds) | mt wall | st engine |
|---|---|---|---|---|
| pgo | 1,591 / 34 | +3.2% (+2.7 to +3.7) | +1.4% | +14.7% |
| engine | 2,066 / 26 | **−0.1% (−0.7 to +0.5)** | −0.1% | +11.9% |
| frac | 2,423 / 35 | +1.1% (+0.0 to +2.1) | **−4.6%** | +13.1% |

- **Diagnosis confirmed.** In `engine`, the "unlikely" refusal for
  `increase_evaluation` is gone and the 3% loss disappears. Some calls stay
  out of line, correctly: `decrement_visits` is on the rare undo path and is
  reported as unlikely in every arm.
- **Fixed, PGO is neutral.** The LTO build already inlines nearly everything
  on the hot path, so there is little left for PGO to rearrange. The engine is
  bound by cache misses (entries 23, 25), which PGO does not touch.
- **`frac` made the CPU network faster, not the engine.** Wall time −4.6% at
  +1.1% engine time, so the gain is in `Mlp`. That is the CPU stand-in the GPU
  replaces, so it is not a production gain.
- **The stub is 12–15% slower in every arm.** A profile from real-network
  games mis-optimizes a different workload (the stub's trees differ, entry
  22). That is a production concern too: testing mode and future engine
  changes would each need a fresh, matching profile.

## Verdict

**Do not adopt PGO.** It is bit-identical but gives no gain on the production
workload, and it is fragile to the workload. The harness stays: it runs any set
of build variants through the same gates and paired timing, and can be reused
for the compiler comparison.

## Discussed with the developer, not yet done

- **Manual hints** give PGO's useful half deterministically, with no training
  run:
  - `__attribute__((cold))` / `__builtin_expect` on rare paths (undo, logging,
    errors);
  - `always_inline` / `flatten` for inlining;
  - `__builtin_prefetch`, which is the most promising. Backup is bound by
    cold-line misses (entry 25), and neither PGO nor inlining can hide those.
- **C++20** would make hints readable (`[[likely]]`, `std::bit_cast`,
  `<bit>`), but it gives no speed by itself. It needs changing the standard
  flag in the bench Makefile, CMake and `setup.py`, then the gates. It is only
  worth doing if we take the hints route. C++23 adds `[[assume]]` and little
  else for us.
- **Other compilers** (web research, 2026-09-24):
  - clang and GCC trade wins within a few percent in 2026 benchmarks, but a
    branchy search engine is worth one A/B;
  - LLVM's MLGO (trained inlining and register allocation) gives modest gains
    and usually needs a custom clang build;
  - BOLT can run in instrumentation mode, which does not need `perf`;
  - Intel icpx helps mostly numeric code;
  - LLM superoptimizers are research: SuperCoder was ~1.4× on small programs,
    with 95% correctness, not 100%.

  Next: clang-20 and g++-14 arms in this harness, after the developer
  installs them (`apt install clang-20 g++-14`; the dry run adds packages
  only and upgrades none of the libraries the benchmarks load). Bit-identity
  across compilers is not guaranteed (contraction, libm), so the digests
  decide.
